# Claude Desk 运行中消息队列与“调整方向”设计

## 背景

Claude Desk 当前只允许空闲会话发送消息。任务进入 `starting`、`running`、`awaiting_permission` 或 `stopping` 后，输入框会被禁用；Rust 协调器也会用 `task_already_running` 拒绝第二次 `send_turn`。这使用户无法像 Codex 一样在 Claude 工作期间继续整理并提交后续指令，也不能把一条已经排队的消息立即注入当前任务。

本次改动复刻 Codex 的核心交互：主输入区始终用于普通发送；运行中提交的消息进入输入框上方的等待队列；每条等待消息提供“调整方向”操作，用户明确点击后才把它作为实时指令发送给当前 Claude SDK 查询。

## 目标

- 任务运行时仍可输入并提交普通消息。
- 运行中提交的消息按提交顺序显示在输入框上方。
- 等待消息支持“调整方向”、删除和编辑。
- “调整方向”使用 Claude Agent SDK 的流式输入和 `priority: "now"`，保留当前进度并尽快影响当前任务。
- 当前任务正常完成后，等待消息按 FIFO 顺序自动开始下一轮。
- 当前任务失败或被停止时不自动执行等待消息，避免意外修改文件。
- 不同任务的消息队列和实时调整严格隔离，兼容现有并行任务能力。

## 非目标

- 不实现跨应用重启的等待消息恢复。
- 不改变权限审批、用户问题卡片或设置同步流程。
- 不改变 Claude 原生会话历史的存储格式。
- 不实现队列拖拽排序、批量操作或定时发送。
- 不把主发送按钮改名为“立即调整”。

## 用户体验

### 空闲状态

- 输入框维持当前 Claude 主题与圆角面板样式。
- 占位文字使用“随心输入”。
- 点击主发送按钮或按 `Cmd/Ctrl + Enter`，消息立即启动新一轮。

### 运行状态

- 输入框保持可编辑，主发送按钮外观和含义仍为普通“发送”。
- 点击发送后，消息不会立即打断当前任务，而是进入输入框上方的等待消息区。
- 等待消息不立刻出现在对话时间线中；只有真正发送给 Claude 后，才显示为右侧用户消息。
- 多条等待消息按 FIFO 排列。等待区设置最大高度，超出后内部滚动，避免挤压对话区域。

等待消息行采用参考图的结构，并适配现有深色 Claude 主题：

```text
┌──────────────────────────────────────────────────────────┐
│ ↳  消息摘要                         调整方向   删除   … 更多 │
├──────────────────────────────────────────────────────────┤
│ 随心输入…                                               │
│                                         [普通发送按钮]   │
└──────────────────────────────────────────────────────────┘
```

- 左侧显示排队图标和单行消息摘要，过长内容省略，悬停可查看完整文本。
- “调整方向”是文字操作，位置和层级与参考图一致，不占用主发送按钮。
- 删除按钮直接移除该条等待消息。
- 更多按钮打开小菜单，当前最小闭环只提供“编辑消息”。编辑在原消息行内完成，支持保存和取消。

### 状态差异

- `starting`、`running`：允许普通消息排队，也允许“调整方向”。
- `awaiting_permission`：允许继续排队，但暂时禁用“调整方向”，提示“请先处理权限请求”。
- `stopping`：允许保留现有队列，但拒绝新增调整；新消息仍可排队，等待停止结果。
- `completed`、`idle`：如果存在等待消息，最前一条由协调器自动启动。
- `failed`、`interrupted`：不自动执行队列；消息继续显示，操作由“调整方向”变为“立即发送”。

## 架构

### 前端

`ComposerBox.vue` 负责编辑框、等待消息列表和行级操作的展示，不自行判断一条提交最终是立即运行还是进入队列。`ConversationView.vue` 负责把当前任务状态、等待消息和操作事件连接起来。`App.vue` 调用统一的提交与队列 IPC，并处理失败提示。

前端维护按任务索引的队列快照。首次进入任务或切换任务时调用读取接口，运行过程中通过 Tauri 队列变更事件更新快照。后端返回成功前不清空输入；提交失败时保留原文本。

建议新增以下前端模型：

```ts
interface QueuedTurnDto {
  id: string
  taskId: string
  text: string
  createdAt: string
}

type TurnSubmission =
  | { kind: 'started'; runId: string }
  | { kind: 'queued'; queuedTurn: QueuedTurnDto }
```

### Tauri IPC

使用统一的 `submit_turn` 代替 UI 对 `send_turn` 的状态判断。协调器在一个临界区内判断任务是否正在运行：空闲时启动新一轮，运行时创建等待消息。这能消除“前端看到空闲、后端仍在清理”造成的竞态。

新增或调整以下命令：

- `submit_turn(task_id, prompt) -> TurnSubmission`
- `list_queued_turns(task_id) -> Vec<QueuedTurnDto>`
- `update_queued_turn(task_id, queued_turn_id, prompt) -> QueuedTurnDto`
- `delete_queued_turn(task_id, queued_turn_id)`
- `adjust_queued_turn(task_id, queued_turn_id)`
- `send_queued_turn(task_id, queued_turn_id)`：用于失败或停止后的“立即发送”

现有 `send_turn` 可保留为内部启动能力或兼容接口，但新 UI 只调用 `submit_turn`。

### Rust 任务协调器

协调器新增两类状态：

- `running` 条目增加当前 `run_id` 和一个独立控制通道发送端。
- `queued_turns` 按 `task_id` 保存 `VecDeque<QueuedTurnDto>`。

每个运行任务的后台循环同时监听 Bridge 事件、停止信号和控制通道。`adjust_queued_turn` 从对应任务的队列中原子领取消息，并通过控制通道交给当前 Bridge。Bridge 确认接收后，协调器删除队列项并发布现有 `user_message` 事件；失败时把消息恢复到原队列位置并返回可恢复错误。

任务正常完成后，协调器先从 `running` 移除旧运行，再领取队首消息启动新一轮，避免新的 `submit_turn` 被错误判定为仍在运行。队列中的其余消息保持原顺序。失败或中断只更新任务状态，不自动领取队列。

队列仅保存在当前应用进程内。应用退出时，现有退出确认流程停止运行任务，未执行队列随进程结束。

### Bridge 与 Claude Agent SDK

Bridge 把 `query({ prompt: string })` 改为由可推送异步迭代器驱动的流式输入：

- 首条消息以普通 `SDKUserMessage` 写入输入流。
- 新增 `run.adjust` 控制消息，包含 `adjustmentId` 和文本。
- Bridge 收到后写入带 `priority: "now"` 的 `SDKUserMessage`。
- Bridge 返回 `run.adjust.accepted`；无法接收时返回 `run.adjust.rejected` 和原因。
- SDK 查询仍使用同一个进程、会话和 `runId`，不会因调整重启。
- 查询产生本轮最终结果后关闭输入流并完成当前运行。

Bridge 控制协议保持版本 `v: 1`，新消息类型按向后兼容方式加入。旧 Bridge 不识别 `run.adjust` 时会返回明确错误，Rust 将等待消息恢复到队列。

## 数据流

### 运行中普通发送

1. 用户提交文本。
2. 前端调用 `submit_turn`。
3. 协调器发现任务正在运行，生成唯一队列 ID 并追加到该任务的 FIFO。
4. 后端广播新的队列快照。
5. 前端清空输入，在输入框上方显示等待消息行。

### 调整方向

1. 用户点击某条消息的“调整方向”。
2. 前端调用 `adjust_queued_turn` 并把该行标记为处理中，避免重复点击。
3. 协调器原子领取该消息，通过当前任务控制通道发送 `run.adjust`。
4. Bridge 把消息作为 `priority: "now"` 的 SDK 用户消息推入当前查询，并确认接收。
5. 协调器发布 `user_message`，删除队列项并广播快照。
6. 对话时间线显示新的右侧用户消息，Claude 在当前运行内继续处理。

### 自动开始下一轮

1. 当前任务以 `completed` 结束。
2. 协调器完成旧运行清理并领取队首消息。
3. 该消息按普通新一轮启动，获得新的 `runId`。
4. 协调器发布 `user_message` 并广播剩余队列。
5. 其余等待消息继续保持 FIFO。

## 竞态与错误处理

- 所有队列修改都以 `queued_turn_id` 定位，重复操作返回幂等结果或明确的“消息已处理”错误。
- “调整方向”与当前任务完成同时发生时，协调器只允许一个路径领取消息：成功交给当前 Bridge，或在旧运行清理后立即作为下一轮启动；不会重复执行或丢失。
- Bridge 拒绝、控制通道关闭或写入失败时，消息恢复到原队列位置，前端显示行级错误。
- 普通提交失败时保留输入内容，不生成等待行。
- 编辑后仍执行空白和 200,000 字符长度校验。
- 切换任务不会串队列；所有命令同时校验 `task_id` 和 `queued_turn_id` 的归属。
- 等待权限时“调整方向”在前端禁用，后端也做同样校验，防止绕过 UI。

## 测试策略

### 前端测试

- 空闲和运行状态下输入框均可编辑。
- 主发送按钮在运行中不变为“立即调整”。
- 运行中提交后出现等待消息行，时间线暂不出现用户气泡。
- “调整方向”、删除、编辑、失败后“立即发送”的事件和禁用状态正确。
- 多条等待消息按顺序显示，切换任务不会混淆。
- IPC 失败时输入或等待消息内容不丢失。

### Bridge 测试

- 首条 Prompt 通过异步输入流送入 SDK。
- `run.adjust` 转换为 `priority: "now"` 的 `SDKUserMessage`。
- 接收、拒绝、停止和权限控制消息可以并存。
- 查询结束会关闭输入流，不遗留控制协程。

### Rust 测试

- `submit_turn` 能原子地区分立即启动与入队。
- FIFO 自动续跑只在 `completed` 后发生。
- `failed` 和 `interrupted` 保留队列且不自动执行。
- 实时调整成功、Bridge 拒绝恢复、重复点击和完成竞态均不丢失或重复消息。
- 多任务并行时控制通道和队列严格隔离。

- 运行前端单元测试、类型检查和生产构建。
- 运行 Bridge 单元测试、类型检查和 sidecar 构建测试。

## 验收标准

- 任务运行时可继续发送消息，消息以参考图样式出现在输入框上方。
- 主发送按钮始终保持普通发送，不被“调整方向”替换。
- 当前任务仍在运行时点击“调整方向”，Claude 进程和 `runId` 不变，新指令进入同一 SDK 查询。
- 正常完成后队列按 FIFO 自动执行；失败或停止后不会自动执行。
- 编辑、删除和立即发送均能形成完整闭环。
- 切换任务和多任务并行不会串消息。
- 所有新增测试及现有回归测试通过。
